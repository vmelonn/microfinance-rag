Internship project · design brief

microfinance-rag

A retrieval layer over the existing payment platform. Separate repository, same OpenShift namespace, four read-only seams. It puts a question box on the operator console and answers with citations drawn from the platform's own documentation and trace history.

Why this exists

The RPA brief argued that the strongest RAG use case in microfinance operations is a copilot that helps an operator resolve an exception, because the corpus accumulates as a byproduct of the work and every answer is checkable by the person receiving it.

That version is blocked on things outside this project: RSA credentials, vendor access, PII approval, and a history of resolved cases that does not exist yet. This is the same architecture pointed at a system we fully own. Nothing here is blocked, the data is synthetic, and the result runs end to end.

What it actually answers

The same three-way routing from the ops design, made concrete against this platform. The split matters because mixing counting with reading is how a system produces a confident wrong number.

A question like thisGoes here
How many authorizations failed with code 51 today? Text to SQL over ClickHouse. Counted, never retrieved.
What is the balance on 03001234567? Direct lookup against ledger-service. Exact value; the model only words it.
What happens if the ledger posting fails after the switch approved? Retrieval over architecture.html and the saga docstrings.
Why did correlation ID abc-123 fail? Both. Fetch the trace, then retrieve what its failure mode means.

That last row is the reason this is worth building. It is the shape every real operational question takes: some facts, some reading, and a person who needs both at once.

The corpus already exists in the repo

docs/architecture.html131 KB, including ten scenarios recorded from the services' own logs
docs/practice-schema.html31 KB, ledger schema and its invariants
docs/sql-practice.md17 KB, query patterns over the warehouse
README.md13 KB, layer map and the service and port matrix
Service docstringsidempotency.py and transaction-service/main.py carry real prose about races and compensations

How it connects

Correlation IDs propagate inward from the gateway exactly as they do everywhere else in the platform, so a question is traceable through the same console tooling as a payment.

Why a separate repository rather than services/rag-service

The dependency footprint. This service needs sentence-transformers and torch, a multi-gigabyte image sitting beside the platform's lean FastAPI ones, and it would slow every build in the existing matrix. Keeping it separate keeps that weight off the payment path. The cost is a second pipeline and a second deploy, which is worth paying here.

Layout

microfinance-rag/
  PLAN.md  README.md  requirements.txt  Makefile
  docker-compose.yml          local: pgvector + the service
  app/
    main.py                   FastAPI, mirroring services/_base conventions
    config.py                 env only, no literals
    ingest/
      loaders.py              html, markdown, python source
      chunker.py              structure-aware: heading, scenario, docstring
      metadata.py             doc_type, source_uri, section_path, status
      embedder.py             runs offline, not in the cluster
      pipeline.py             idempotent on content hash
    retrieve/
      store.py                pgvector and tsvector queries
      hybrid.py               vector + BM25, reciprocal rank fusion
      rerank.py               cross-encoder, 30 -> 5
      filters.py              hard predicates, applied before similarity
    answer/
      router.py               structured vs retrieval vs lookup
      sql_tool.py             read-only, view-scoped, row-limited, statement logged
      prompt.py
      llm.py
      citations.py            every quote verified against its source
    api/
      routes.py               /ask, /ingest, /healthz
  db/migrations/            documents, chunks, HNSW and GIN indexes
  eval/
    questions.yaml            the held-out set
    run_eval.py               retrieval@k and answer quality, scored separately
  openshift/base/           Deployment, Service, kustomization
  tests/

Four modules, one job each, in the order a request travels. retrieve/ never imports answer/, and answer/ never touches the database directly. That separation is what lets the eval measure retrieval quality independently of answer quality, which is the most useful thing the eval does.

Feasibility

High, and for one specific reason: every blocker from the company version is absent. No RSA, no vendor portal, no PII approval, no waiting for a case history to accumulate. The corpus is committed to the repo today, Postgres 16 is already running, and the namespace already exists.

The real work is chunking HTML sensibly, getting hybrid retrieval to fuse properly, and writing an honest evaluation set. None of that is research. It is all engineering with known answers, which is exactly what an internship project should be.

Limits, stated plainly

These are the things that would make this a weak project if left unsaid.

1

The corpus is small enough that RAG may not beat keyword search

About 196 KB of documentation, which chunks to somewhere in the low hundreds. At that scale a tuned BM25 index performs close to a vector index, because there is not enough semantic variety for embeddings to earn their cost. Frame the deliverable honestly: this demonstrates the architecture and produces a working eval harness. Then make the eval do real work by measuring both, because "we measured, and BM25 was within noise on a 400 chunk corpus" is a genuinely good finding and a more credible one than a claimed win.

2

The namespace almost certainly cannot host an embedding model

The manifests are frugal for a reason. Twelve workloads, services requesting 50m CPU and 128Mi, ClickHouse alone at 3Gi, and comments in ace-stub.yaml and api-gateway.yaml describing a namespace LimitRange that injects a 1 CPU default plus a ReplicaSet quota of thirty. A sentence-transformers container wanting 1 to 2Gi resident does not fit into what is left.

Resolution: split ingest from query. Ingest runs offline, on a laptop or in CI, where a full-size model is free, and writes vectors into Postgres. At query time the service embeds exactly one short string, which a quantized 300 MB model can do, or which can be skipped by running keyword-only retrieval in the cluster and reserving vector search for local development. Design for this from the start rather than discovering it at deploy time.

3

postgres:16-alpine does not ship pgvector

openshift/base/datastores.yaml uses the stock Alpine image, which has no vector extension. It needs pgvector/pgvector:pg16. That is a one line change, but it touches the datastore the ledger depends on. Since the ledger's data matters and the index's does not, stand up a second Postgres rather than swapping the image underneath the ledger.

4

Synthetic data means no real feedback loop

There are no operators, so nothing generates accept, edit or reject signal. The eval set has to be hand written, which means it measures what you thought to ask rather than what people actually ask. That is a real ceiling on tuning, and it is why the eval questions should be drawn from the ten recorded scenarios rather than invented.

5

It cannot demonstrate the thing that matters most

The company version's value is measured in operator minutes saved. Here there are no operators and no baseline, so no such number exists. What this can show is that the pipeline works, that citations verify, and that the router sends numeric questions to SQL instead of guessing them. Those are worth showing. Time saved is not available and should not be claimed.

6

It is more interesting than the thing that pays

The MPG fetcher and the reconciliation pilot are what the company actually needs. This is the more enjoyable project and it competes for the same hours. Worth being deliberate about that rather than drifting into it.

Build order

  1. Schema and migrations. documents and chunks, HNSW on the embedding, GIN on the tsvector. Second Postgres instance, per limit 3.
  2. Ingest, offline. Loaders, structure-aware chunker, metadata, embed, write. Verify by counting chunks per source and reading twenty of them by hand.
  3. The eval set, before any tuning. Thirty to fifty questions drawn from the ten recorded scenarios, each with a known correct source. Written first, so retrieval cannot be fitted to it.
  4. Retrieval, measured. Keyword only, and record retrieval@5. Then add vector and fusion, and record it again. The comparison is the deliverable.
  5. Rerank. Measure again. Expect the largest single jump here.
  6. The router and the SQL tool. Read-only, view-scoped, statement shown to the user, so a wrong answer becomes a visible wrong query instead of an invisible wrong number.
  7. Answer and citation verification. Refuse when retrieval is weak.
  8. Console tab, proxied through api-gateway.
  9. Deploy, with query-time embedding sized to whatever the namespace allows.

Steps 3 and 4 are what make this an engineering project rather than a demo. Do not skip to answer generation, which is the easiest part and the least informative.
